Android IME · Offline autocorrect · MIT-licensed app

A GitHub package to give our keyboard Apple-grade autocorrect.

Fully offline: silent typo replace, a 3-word suggestion bar, next-word prediction, and smart auto-capitalize / punctuation — dropped into a native Java InputMethodService that already has the chip strip.

⌨
The One-Sentence Answer

No single permissive package delivers all four Apple behaviors — so layer permissive libraries: JSymSpell (MIT) for correction + a small next-word layer + your own smart rules, or vendor the AOSP LatinIME engine (Apache-2.0) for max fidelity. Never bundle GPL keyboards (HeliBoard/OpenBoard) or AOSP's Lexiteria dictionaries.

◆
Tailored for a solo dev's MIT-licensed, Java, offline Android keyboard that already has a suggestion chip strip and platform spell-checker plumbing — figures accurate as of 2026-05-17.
01

Why this answer

1

License is the real constraint, not capability. The best turnkey engines (HeliBoard, OpenBoard) are GPL-3.0. An APK is one conveyed binary with no linking escape hatch, so bundling their code would force your whole MIT app to GPL. Only Apache-2.0 and MIT/BSD code is safe to ship.

2

"Apple-like" is a scoring engine, not a spellchecker. The piece plain spellcheckers lack is a keyboard key-proximity model — weighting corrections by physical key distance is what makes fat-finger fixes feel native. That, plus an n-gram language model and a confidence-gated silent replace, is the whole trick.

3

Your platform spell-checker can't get you there. SpellCheckerSession is async, depends on whatever checker the user installed, and has no proximity model, no next-word prediction, and no controllable silent replace. Demote it to a fallback; make a bundled in-process engine the source of truth.

4

You already own the hard plumbing. The chip strip, a pending-correction concept, and commit hooks are done. The work is swapping a real correction engine behind them and adding deterministic smart rules — not rebuilding the keyboard.

↔ Independent agreement

  • ›GPL-3.0 = do not bundle in an MIT app; Apache-2.0 / MIT = safe; LGPL is high-friction on Android; AGPL avoid.

  • ›The 5-layer architecture is identical in both passes: dictionary + frequency → proximity candidate generation from the tap stream → n-gram LM scoring → confidence-gated silent replace with a typed-word escape hatch + backspace revert → commit-time smart rules.
  • ›Next-word prediction = when no word is composing, feed n-gram successors of the last word(s) into the same 3-chip strip; learn user n-grams on-device and demote rejected corrections.
  • ›SCOWL / ESDB is the safe permissive base lexicon; FlorisBoard's NLP core isn't shipped yet.

05

How to actually build it

Recommended stack — Path A (ships in days, stays cleanly MIT)

Keep your chip strip. Behind it, layer four permissive pieces instead of chasing one impossible drop-in:

JSymSpell typo replace + suggestions · MIT + Key-proximity weighting from your layout XML + Bigram next-word · AnySoftKeyboard approach · Apache-2.0 + Rules auto-cap · double-space · apostrophes

Data: build the dictionary from SCOWL/ESDB (permissive) + a Google-Books-Ngram-derived frequency table (CC-BY, attribution). Avoid CC-BY-SA data (wordfreq, FrequencyWords, Norvig's big.txt) verbatim in a shipped product.

The engine, in five layers

Think of it as a noisy-channel decoder — the user intended a word, the "channel" (fat fingers) produced the taps, and you recover argmax P(word) × P(taps | word). Concretely:10,12

1 · Lexicon + frequency in a DAWG/trie with a per-word frequency byte — O(word-length) lookup and free prefix completion. Frequency alone already fixes ~80% of typos.11 2 · Candidate generation via Damerau-Levenshtein (transposition counts as one edit, so "teh"→"the" is a single step). Don't brute-force at runtime — SymSpell precomputes deletes, or you walk the DAWG with a Levenshtein-automaton row. Budget edit-distance 1 for short words, 2 for longer.5,10

3 · Key-proximity / touch model — the Apple-defining layer. If you capture tap coordinates, model each touch as a 2-D Gaussian over the intended key; if you only have committed characters, build a key-adjacency map and make substitution cost a function of adjacency (~0.5 for neighbors vs 1.0 for far keys). This is what makes fat-finger fixes feel native.1,12 4 · Language-model scoring blends spatial score with n-gram probability: score = α·spatial + β·unigram + γ·bigram, with stupid-backoff. Next-word prediction is the same table read forward: top bigram successors of the last committed word.3

5 · The auto-replace decision + smart rules. Silently replace only when the typed string isn't itself a common word, the best candidate beats it by a margin, and the edit distance is small — otherwise just show it in the strip. Keep the typed word as a tap-to-reject escape hatch, and make the first backspace after a correction restore the original (Apple/AOSP behavior). Then the cheap deterministic wins: auto-capitalize sentence starts, double-space→". ", an apostrophe lookup table (dont→don't, i→I), and suppress correction entirely in URL/email/password fields.3,7

Wiring it into your InputMethodService

You keep the UI and replace the hot path.14,15 Per keystroke: maintain the composing buffer (and tap coordinates, if you have them), recompute candidates, update setComposingText and push the top 3 to your strip. At a commit boundary (space / punctuation / newline): run the confidence gate, commitText the correction plus separator, store a LastCorrection{original, committed, offset} record, then repopulate the strip with next-word predictions. Use onUpdateSelection only to observe cursor moves and reset state — not to re-trigger correction.

Threading: run the engine on a single background HandlerThread or serial executor; debounce and tag each request with a generation counter so stale results are dropped, then post updates to the main looper. Load the DAWG once at onCreate, memory-mapped. Revert: on the immediate backspace, deleteSurroundingText then commitText(original); any other key or cursor move clears the record. Persist a small user unigram/bigram store (SQLite or a file) separate from the immutable bundled DAWG so the keyboard "stops fighting you."

Budget: an English DAWG + bigram table sits around 5–20 MB resident (mmap'd), per-keystroke compute is sub-5 ms, and end-to-end stays under one 16 ms frame — the debounce is what protects that under fast typing. Codex confirmed from HeliBoard's live source that this exact stack (getSuggestionsNative taking proximityInfo, xCoordinates, yCoordinates, times; getNgramProbabilityNative with up to 3 previous words; separator-triggered auto-correct and backspace revert in InputLogic) is still what ships in 2026.3,6,7

The license bottom line

An APK conveys everything you bundle as one binary — there's no dynamic-linking loophole. So: Apache-2.0 (AOSP LatinIME) and MIT/BSD (JSymSpell) are safe, and Apache-2.0 is the strategically smarter permissive pick because it carries an express patent grant that MIT/BSD lack — worth having in patent-dense keyboard territory. GPL-3.0 (HeliBoard, OpenBoard) would relicense your whole app; read them for approach only. And the subtle trap both the AOSP dictionaries and the popular frequency corpora share: the code can be permissive while the data isn't — AOSP's dictionaries are Lexiteria's, wordfreq/FrequencyWords data is CC-BY-SA. Build your data from SCOWL/ESDB and Google-Books-Ngram instead.2,9,16,17,19 Not legal advice — the GPL-linking question is untested in court; get an attorney's sign-off before a commercial launch.
